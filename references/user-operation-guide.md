# 协作操作手册

## 安装与版本

- macOS 的活跃 Skill 目录通常是 `~/.codex/skills`；Windows 通常是 `%USERPROFILE%\.codex\skills`。
- 普通使用者只保留一个 `mint-report-html`。不使用的 deck Skill 和历史备份应移动到任意用户选择的备份目录，但该目录必须位于活跃 Skill 目录之外。
- 备份位置不依赖 WD、盘符或固定用户名。外接盘只是可选存储，不是 Skill 运行前提。
- 制作前可运行 `node scripts/check-skill-installation.mjs`；检查结果必须为一个 HTML Skill、零个活跃 deck Skill、零个同名历史备份。
- 能力较弱或新安装的 Codex 必须在提示词第一句显式写 `$mint-report-html`，不要只说“帮我做个汇报”。

## 推荐提示词

任务卡由协调人只生成一次：

```text
使用 $mint-report-html，为本次多人协作汇报生成任务卡。

请完整读取领导大纲和已经确定的人员分工。只生成 report.mint-task.json，不制作页面，不补写大纲中不存在的内容，也不要让用户选择字体、颜色、16:9、页眉页脚或页码；这些使用 Skill 内置规则。

任务卡必须保留领导大纲顺序，为每位负责人生成稳定且唯一的 sectionId，并记录负责人、负责的大纲项和章节顺序。如果大纲编号缺失、分工冲突或同一大纲项被多人重复认领，请列出问题并停止猜测。
```

负责人制作章节：

```text
使用 $mint-report-html。

请先完整读取我提供的 report.mint-task.json 和我的全部原始材料。我是【负责人名称/代号】，只制作任务卡中分配给我的章节。

只使用附件中的事实、数字、结论和关系，不联网补写，不擅自改变口径，不得因为控制页数而删除核心内容。先判断每部分在回答什么管理问题；属于同一业务链条、漏斗、因果链、策略体系或管理动作的内容优先合并在同一页。不要因为出现多个数字就机械画图，要根据真实的数据关系选择表格、柱状图、折线图、漏斗、矩阵、流程或关系图；所有图表必须有清晰对象/系列标签、单位和统计周期。

请一次生成我负责的完整章节，输出一个 .mint-section.html 供审阅和最终合并。文件必须是16:9、简洁清新、无页眉页脚页码、可离线发送；按E后标题、正文、表格、图表数据、图片和关系图都必须可以修改并保存。个人阶段不要生成PPTX或PDF，也不要让我管理ZIP。

如果发现任务卡与材料冲突、资料缺失、数值口径冲突或真实容量冲突，请准确列出并停止猜测；除此之外不要反复向我确认排版偏好。
```

最终合并与发布：

```text
使用 $mint-report-html。请读取同一份 report.mint-task.json 和各负责人的当前版 .mint-section.html，按任务卡章节顺序合并。必须保留每个章节中的人工修改、来源台账、编辑能力和内部版本身份；不得重新总结或改写各章节。

先输出一个完整、可编辑、可离线发送的 .mint-report.html 给领导审阅。领导确认后，再从这份当前完整HTML发布最终16:9 PPTX和PDF；不得使用合并前的旧项目，不得出现页眉、页脚、页码、任务卡路径、负责人、大纲编号或其他内部审计信息。PDF不得空白，PPTX不得使用整页截图代替原生可编辑对象。
```

## 协调人

1. 等团队按正常职责认领领导大纲。
2. 把原大纲、汇报名称和已定分工交给 Codex，说“只生成一次协作任务卡，不制作页面”。
3. 把 `report.mint-task.json` 发给所有负责人。
4. 各部分初审完成后，收集每人的“当前版 `.mint-section.html`”和任务卡，一次性交给 Codex 合并。
5. 先把完整 `.mint-report.html` 给领导审阅；确认后再让 Codex 最终发布 PPTX/PDF。

协调人不设置字体、背景、16:9、页眉页脚页码，也不分配具体页码。这些由 Skill 处理。

## 负责人

1. 把任务卡、自己的材料和“我是 A/B/C”交给 Codex。
2. 得到一个 `.mint-section.html`，不用生成个人 PPTX/PDF，也不用管理 ZIP。
3. 双击打开。按 `E` 修改标题和正文；点击表格、图表、图片或关系图修改结构化内容。图片可选择“完整显示/裁切填满”，并调整框内缩放和水平、垂直位置；架构图、截图或含文字图片优先使用“完整显示”。
4. 点击“保存当前版”或按 `Cmd/Ctrl+S`。第一次按浏览器提示选择当前文件；不支持直接保存时，保留下载的新 HTML 作为当前版。
5. 领导要求拆页、并页、换主题或重组时，把当前 HTML 和意见一起交给 Codex，不能只交最初原始材料。
6. 审阅完成后，只把当前版 HTML 发给协调人。文件改名不会破坏身份，但仍建议保留负责人和“当前版”字样便于人看。

## 领导

1. 各负责人完成时间不同，可以分别打开各自 HTML 随到随审。
2. 标题、正文、表格、图表数据、图片和关系图可以直接修改并保存。
3. 需要拆页、并页或改变论证结构时提出意见，由负责人把当前 HTML 交给 Codex 做结构性修改。
4. 各部分初审后看完整合并 HTML；最终 PPTX 中仍可使用 PowerPoint 修改原生对象。

## 最终发布人

1. 确认使用的是任务卡要求的全部当前章节；若系统提示版本分叉，先让负责人明确选哪一份，不能猜。
2. 合并后确认完整 HTML 的章节顺序和内容；领导做过修改时，以领导最后保存的完整工作 HTML 为准。
3. 让 Codex 先从该完整工作 HTML 恢复当前项目，再执行一次 Publish，得到 HTML、PPTX、PDF；不要直接发布合并前的旧目录。
4. 检查 `delivery-manifest.json` 为 `formal-ready`；否则不能把旧文件当作新版本通过。

## 常见问题

- **为什么还要任务卡？** 它不是分工表，而是报告、章节顺序、版本和设计契约的机器身份证，确保独立文件能可靠合并。
- **ZIP 在哪里？** 已经内嵌在工作 HTML 中。正常用户不导出；排障时才用技术 ZIP。
- **图片发出去会不会消失？** 交付门禁要求实际引用素材全部内嵌；外链或本机绝对路径会阻断交付。
- **文件改名怎么办？** 系统读内部身份，不读文件名。
- **两份都叫最终版怎么办？** 相同内容自动去重；严格后代选新；分叉版本阻断并让人选择。
- **为什么个人阶段没有 PPTX/PDF？** 避免每人重复做高耗时格式转换；最终从同一当前模型统一生成一次。
